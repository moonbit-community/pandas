# M3 benchmarks

- Machine: lab5 (Intel Core i9-13900K, 32 threads, 62 GiB RAM, Linux 6.8). The machine is shared:
  the load average was 4 to 7 during the runs (lower than for `m2.md`, where it was 12 to 14), so
  absolute numbers are still somewhat noisy. Compare items within one table, not across tables or
  with `m2.md`.
- Date: 2026-11-24
- Toolchain: moon 0.1.20261119 (738607b 2026-11-19)
- Tree: the merged M3 batches (1) and (2) (`56dee22`) plus the benchmark additions of this task.
- Commands: `moon bench --target native -p smallbearrr/pandas/pl -f <file>` and the same with
  `--target wasm-gc`, run 3 times in a row for `bench_test.mbt` (the 14 "m3" items: `-i 22-32`
  and `-i 32-36`, the second range in a second batch of runs a few minutes after the first) and
  for `join_bench_test.mbt` (all 9 items). Every cell is the **median of the three mean times**;
  the three means follow in brackets, in run order. Each mean is the `moon bench` mean of 10
  rounds.
- Source: `src/pl/bench_test.mbt` (the "m3" items) and `src/pl/join_bench_test.mbt`. Every item
  uses n = 1,000,000 rows; inputs are built outside the timed closure and are deterministic, so
  runs are reproducible.
- The "m3" table (`m3_bench_df`) has three columns: `gi` an `Int64` key with exactly the stated
  number of distinct values (`i * 7919 % groups`, a strided sequence, not a random one: see "Random keys" below), `gs` the same
  key as a `String` (`"key<value>"`) and `v` an `Int64` value (`i % 1000`). The aggregations are
  `col("v").sum()`, `col("v").mean()` and `len()`.

Output sizes (rows):

- The unique-key joins give 1,000,000 rows (Full and Right too: both sides hold the same keys).
- "1M x 1000 right keys repeated 10 times": the left table has 100 distinct keys (Inner item) or
  1 000 keys of which 100 appear on the right (Left item); the right table has 1 000 rows, 10 per
  key. The Inner item returns 10,000,000 rows (every left row has 10 matches), the Left item
  1,900,000 (100,000 left rows with 10 matches, 900,000 with none).
- "right keys all equal 1M x 10" (in `bench_test.mbt`, table above): the left table has 10
  distinct keys, the right table has 10 rows that all carry the key 0. The Inner join returns
  1,000,000 rows, the Left join 1,900,000.

In every one of these the cost follows the output size, not the product of the input sizes. The
string-key item shares a 60-character prefix between all keys; it costs about three times the
`Int64` join because every hash and comparison reads the whole string, and is nowhere near
quadratic.

## Reading the numbers

- All items take between 17 ms and 500 ms on native. The slowest, the string join with a long
  common prefix, is dominated by hashing and comparing 60+ byte keys.
- wasm-gc is 0.95 to 1.8 times native (the string join is the one case where it is faster); the
  largest gap is the join that produces 10M rows, where memory traffic of the output dominates.
- Against the `sort` items in `m2.md` (315 ms for an `Int64` key, 623 ms for a `String` key; those
  runs were on a busier machine, so this is only a rough comparison), a `group_by` with one key
  and three aggregations over 1,000,000 rows costs between a tenth and a fifth of the sort of
  the same size, because it hashes once and never orders the rows.
- The `Cross` join is not benchmarked: its output is the product of the inputs by definition.

## Random keys, and why the tables above are optimistic

The key generators of the tables above are strided, not random: `m3_bench_df`
uses `i * 7919 % groups` and the join frames use `i * 7 % n` and `i * 3 % n`.
Such a sequence visits the table almost in order, so the hash probes and the
gathers are cache-friendly, and the tables above are the best case for the
number of groups and the key order. The table below is the same set of items with
**randomly shuffled keys**: the key column is `i % groups` for every row, then
shuffled in place with a Fisher-Yates shuffle driven by the fixed LCG of
`bench_test.mbt` (`lcg_next`; seeds 12345 for the group keys, 1 and 2 for the
unique join keys, 3 for the right keys of the repeated-key join). Every key
has exactly the stated number of occurrences. Nothing else changed: the same
tables, aggregations and sizes (1,000,000 rows), native release build.

```moonbit
fn shuffled_keys(groups : Int32, seed : UInt64) -> Array[Int64] {
  let a : Array[Int64] = Array::makei(bench_n, i => (i % groups).to_int64())
  let mut st = seed
  let mut i = bench_n - 1
  while i > 0 {
    let (next, j) = lcg_next(st, i + 1)
    st = next
    let t = a[i]
    a[i] = a[j]
    a[j] = t
    i -= 1
  }
  a
}
```

Method (tree `bd5407a`): `moon bench --target native -p smallbearrr/pandas/pl`, 3 runs in a row,
every cell the **median of the three mean times**; the strided column was
measured again in the same session (load average 4 to 6), so the two columns
are comparable; the first strided column is the table above, kept for
reference. Random / strided is the ratio of the random time to the re-run strided time.

What to take from it:

- With few groups the key order does not matter (1.0 to 1.1 times). The cost
  appears when the hash table no longer fits in cache: 500 000 groups cost 1.4
  to 3.1 times the strided figure, and the `String` key suffers most because
  every probe also chases a pointer to the text.
- Joins with unique keys cost about 280 to 290 ms for random keys, 1.5 to 1.8
  times the strided figure; the repeated-key joins about 2.6 times. All are
  still linear in input plus output and below 0.3 s.
- The earlier claim "nothing is above 1 s and nothing is quadratic" still
  holds for random keys: the largest random-key figure of the fast kernels is
  the 290 ms Full join. Use the random column when you estimate a real
  workload, and the strided tables above only to compare items with one
  another.
- The strided join figures in this session varied a lot between runs (the
  three means of `join inner int64 unique keys` were 191, 220 and 147 ms),
  the random ones did not (283 to 287 ms); the machine is shared, so read a
  difference below about 1.3 times as noise.

## The `group_by` slow path

`group_by(...).agg(...)` has a fast path and a slow one, chosen for each
aggregation. The fast path is an aggregation of an expression that works row
by row: a column, a literal, arithmetic and comparisons, `cast`, `is_null`,
`is_in`, `fill_null`, `between`, `when`, `str()` and `dt()` functions and
element-wise functions on those (`col("v").sum()`,
`(col("units") * col("price")).sum()`, `col("x").is_null().sum()`,
`col("v").max()`, `n_unique`, ...; `len()` needs no expression at all). The
expression is evaluated once on the whole table and the aggregation runs over
all groups in one pass.

An aggregation of an expression that looks at other rows of the group takes
the slow path: for every group the rows are gathered into a small table, the
expression is evaluated on it, and the one value is read back, **group by
group**. Examples:

- another aggregation inside the aggregated expression: `(col("v") - col("v").mean()).sum()`;
- a running or neighbouring value: `col("v").cum_sum().last()`, `col("v").shift().sum()`, `col("v").diff().max()`;
- ordering and ranking: `col("v").sort().first()`, `col("id").sort_by([col("v")]).first()`, `col("v").rank().max()`;
- cutting, filtering, `any`/`all`, or a window: `col("v").filter(col("v").gt(lit_int(0))).sum()`, `col("v").unique().len()`, `col("v").head(n=2).sum()`, `col("v").sum().over(...).first()`.

The result is the same; only the cost differs. It grows with the number of
groups, about 1 to 2 microseconds per group, plus about 20 ns per row for the
gathering. Measured on the random-key table of this file (1,000,000 rows,
native release, median of 3 means):

| `agg` over an `Int64` key | 1 000 groups | 500 000 groups |
| --- | --- | --- |
| `col("v").sum()` (fast path) | about 25 ms (the `sum/mean/len` row above) | **82.19 ms** (73.76 / 82.19 / 82.41) |
| `(col("v") - col("v").mean()).sum()` | **48.48 ms** (49.14 / 47.89 / 48.48) | **1 020 ms** (1 010 / 1 020 / 1 020) |
| `col("v").sort().first()` | not measured | **615.46 ms** (623.27 / 615.46 / 614.72) |
| `col("v").cum_sum().last()` | not measured | **529.94 ms** (526.51 / 538.07 / 529.94) |
| the first one rewritten (below) | not measured | **176 ms** (176 / 211 / 153) |

At 500 000 groups the three slow items cost 1.9, 1.1 and 0.9 microseconds per
group more than the fast path (for example (1 020 - 82) ms / 500 000), which is
12, 7.5 and 6.5 times the fast path: one aggregation over a million rows split
in half a million groups takes 1.0 s. With a few large groups the difference is
small (about 2 times at 1 000 groups). The cost is linear, not a defect, and the
same one as the `over` slow path in `docs/golden/known-diffs/window.md`
("Cost").

When it matters, move the part that looks at the group out of the aggregation:
compute it with a window in `with_columns` (one pass), then aggregate the new
column on the fast path.

```moonbit
// slow path: 1 020 ms at 500 000 groups
df.group_by([col("g")]).agg([(col("v") - col("v").mean()).sum()])
// fast path after a window: 176 ms
df
.with_columns([(col("v") - col("v").mean().over([col("g")])).alias("d")])
.group_by([col("g")])
.agg([col("d").sum()])
```

The random-key and slow-path items above are not in `bench_test.mbt` yet; the
key generator shown above and the expressions in the tables are all that is
needed to add them.
