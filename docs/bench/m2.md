# M2 benchmarks

- Machine: lab5 (Intel Core i9-13900K, 32 threads, 62 GiB RAM, Linux 6.8). The machine is shared:
  the load average was 12 to 14 during every run and free memory was low, so absolute numbers are
  noisier than a quiet machine would give. Compare items within one table, not across tables.
- Date: 2026-11-23
- Toolchain: moon 0.1.20261119 (738607b 2026-11-19)
- Commands: `moon bench --target native -p smallbearrr/pandas/pl` and
  `moon bench --target wasm-gc -p smallbearrr/pandas/pl`, each run 3 times in a row (29 bench
  tests per run). Every cell is the **median of the three mean times**; the three means follow in
  brackets, in run order. Each mean is the `moon bench` mean of 10 rounds.
- Source: `src/pl/bench_test.mbt` (the M1 items and the "m2" items below), `src/pl/sort_bench_test.mbt`
  and `src/pl/frame_ops_bench_test.mbt`. Every item uses n = 1,000,000 rows unless the name says
  otherwise; inputs are built outside the timed closure from a fixed-seed LCG, so runs are
  reproducible.
- The "m2" table has four columns: `a` random `Int64` in `0..<n` (about 632k distinct values),
  `b` a `Float64` ramp, `g` random `Int64` in `0..<100`, `s` a `String` key `"k<random>"`.

### `str -> f64` after the m1x fix

The `str -> f64` figure in `docs/bench/m1.md` (144.01 ms after the first fix round, 170.47 ms
before) is out of date: the m1x fixes changed the `String` to `Float64` cast. On the current tree,
1,000,000 rows of `"<i>.<i % 1000>"` take **82.11 ms on native** (three means: 82.06 / 82.42 /
82.11 ms) and 187.56 ms on wasm-gc.

There is no regression against M1. `Series::int64` construct (412 us vs 805 us) and `gather`
(8.70 ms vs 14.74 ms) look slower only because the M1 numbers are single runs and these are
medians on a loaded machine. A review that ran the M1 tree (`a0b4c0c`) and this tree back to back
on lab5, five rounds each, found the same best-of-ten minima (`Series::int64` 358 vs 359 us,
`gather` 7.8 vs 7.1 ms) and medians of the round means of 514 vs 399 us and 11.09 vs 10.40 ms.
The same noise goes the other way too: `Bitmap::bit_and` (identical code) went from 85 us to 48.5 us.

## Final fix round: string and integer hash, deep chains

The tables above were measured before this round (head/tail, `subset?`, the new hash, the
quantile selection and the single sort in `describe` came after them). The items they touch
are measured again here, old tree against new tree in one run per target, one tree after the
other on the same loaded lab5 (load average about 10), so a ratio is more reliable than an
absolute number. Source: `src/pl/sort_bench_test.mbt` (same file on both trees; it uses no
API that changed). Each cell is the `moon bench` mean of 10 rounds, one run. The old tree is the
base of the round (`3f84874`).

### The hash

Integers and strings are hashed with a deterministic two-lane 32-bit scheme
(`src/pl/hashing.mbt`: `hash_int64`, `hash_string`, `hash_finalize`), 32-bit multiplications
only, so it is cheap on js, where `Int64` is slow. The older string hash (32-bit FNV-1a over the
UTF-16 units) had a multicollision: 65,536 strings built from 16 pairs of equal-length blocks (every choice of one block per pair)
with the same hash made `unique` and `is_in` quadratic.

| Item | old native | new native | old wasm-gc | new wasm-gc | old js | new js |
| --- | --- | --- | --- | --- | --- | --- |
| `Series::sort int64 random n=1000000` | 181.31 ms | 173.59 ms | 243.38 ms | 210.14 ms | 1.18 s | 1.36 s |
| `Series::arg_sort int64 random n=1000000` | 156.97 ms | 178.59 ms | 188.13 ms | 195.23 ms | 1.32 s | 1.65 s |
| `Series::unique int64 random n=1000000` | 36.09 ms | 40.08 ms | 48.05 ms | 53.11 ms | 959.98 ms | **358.12 ms** |
| `Series::is_in int64 n=1000000 in 100000` | 35.72 ms | 33.49 ms | 41.00 ms | 40.13 ms | 879.67 ms | **460.36 ms** |
| `Series::sort string random n=200000` | 74.19 ms | 63.81 ms | 72.37 ms | 72.26 ms | 100.03 ms | 117.26 ms |
| `Series::unique int64 composite ids n=1000000` | 75.02 ms | 54.42 ms | 78.17 ms | 75.08 ms | 702.08 ms | **332.90 ms** |
| `Series::unique string random n=1000000` | 170.26 ms | 177.66 ms | 218.40 ms | 201.42 ms | 377.42 ms | 380.87 ms |
| `Series::is_in string n=1000000 in 100000` | 41.09 ms | 51.43 ms | 67.21 ms | 70.51 ms | 218.60 ms | 220.29 ms |

(`sort` and `arg_sort` do not hash; their differences are the noise of the run.) The 1,000,000
row string `unique` on js is **380.87 ms** (old 377.42 ms) and `is_in` 220.29 ms (old 218.60 ms),
so the string hash costs nothing measurable on js; on native the string `is_in` is about 10 ms
slower (51.43 against 41.09 ms; the difference is about one standard deviation of the new run) and the string
`unique` 7 ms slower. The integer hash is what made js slow: `Series::unique` of an `Int64` and
the composite ids take about 2.5 times and 2 times less time on js now.

same file):

| `Series::is_in` | 24.03 s (22.51 to 26.67 s) | **7.43 ms** | 33.25 s (30.73 to 35.78 s) | **24.89 ms** |

### Deep chains (`bench_test.mbt`, native)

`a + 1 + 1 + ...` printed with `Expr::to_string`, and a chain of `lit_int(1) + lit_int(1) + ...`
(weak literals) evaluated by `select`. Both were quadratic before this round (`ExprNode::text`
concatenated the whole left spine at every level and `fold_weak` folded every level again); now
doubling the length doubles the time.

| Item | native |
| --- | --- |
| `Expr::to_string` chain of 5000 terms | 654.89 us |
| `Expr::to_string` chain of 10000 terms | 1.36 ms |
| `select` of a weak literal chain of 5000 terms | 1.59 ms |
| `select` of a weak literal chain of 10000 terms | 3.12 ms |

The depth the stack allows is a separate limit, per backend: see "链的深度" in
`docs/golden/known-diffs/expr_agg.md` (700 terms on wasm and wasm-gc, 500 on js, 10000 on native
for `col + lit + lit ...`).

### What else changed since the tables above

- `DataFrame::head`/`tail` default to 5 rows (no cost change).
- `Series::median`/`quantile` and the percentiles of `describe` pick by selection instead of
  sorting a copy, and `describe` sorts each column once. These were not re-measured: the
  `describe 4 columns n=1000000` figure above is from before the round.
- `vstack`/`append` copy everything on every call; 1000 calls on 1000-row chunks take about 30 s,
  one `concat` of the same chunks 52 ms (documented in the doc comments and `docs/migration.md`).
